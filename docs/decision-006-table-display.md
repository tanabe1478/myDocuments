# ADR-006: Markdown の表を、カーソルが表の外にあるとき表の形で表示する（ADR-004 の延長）

## Status

Accepted（2026-11-09、承認者: プロジェクトオーナー）。ADR-004（カーソルのない行で記号を隠す）を、表に広げる。仕様 §5.2（標準はソースの編集。表示は表示上のもので、本文に不要な自動変更を加えない。ソースの安定を犠牲にして WYSIWYG を入れない）と ED-09（表を損なわない）に従う。仕様の文書そのもの（`docs/spec/`）は書き換えない。

## Context

これまで、Markdown の表（GFM のパイプの表）には専用の表示がなく、`|` と区切りの行が、本文と同じ比例フォントの普通の文字として並んでいた。列がそろわないので、表として読みづらい。

他のエディタが表をどう扱うかを、各製品の文書で調べた（親が文書を読んだ結果で、アプリは動かしていない）。

- 表のまま直接編集する型。Typora は、ツールバーで大きさ・配置・削除を行い、Cmd/Ctrl+Enter で行を足し、行と列をドラッグで動かす（https://support.typora.io/Table-Editing 、https://support.typora.io/Markdown-Reference/ ）。Obsidian は 1.5 以降、右クリックで行と列の追加・削除・並べ替え・移動・配置を行い、1.5.8 で入力中に原文の列を自動でそろえる（https://obsidian.md/help/Editing+and+formatting/Advanced+formatting+syntax 、https://obsidian.md/de/changelog/2024-02-22-desktop-v1.5.8/ ）。Bear 2 は、セルのメニューで行と列を足す（https://bear.app/faq/how-to-use-tables-in-bear/ ）。
- 表で見せ、カーソルのあるセルだけ原文にする型。Zettlr 4.0 は、Tab / Shift+Tab でセルを移り、最後のセルの Tab で行を足す。`|` をそろえる整形は明示のコマンドで、等幅フォントが要る。パイプの表だけを扱う（https://docs.zettlr.com/en/editor/tables/ 、https://www.zettlr.com/post/zettlr-400-released ）。
- 原文のまま、整形を補助する型。iA Writer は、メニューで表のセルを作る。Windows 版は Format → Table → Reformat（https://ia.net/writer/support/basics/markdown-guide ）。VS Code の拡張と mte-kernel は、Tab でセルを移り、そのときに整形する（https://npmjs.com/package/@susisu/mte-kernel 、https://github.com/philipparndt/vscode-markdown-tables ）。
- どの型でも、保存はパイプの表。セルの中の改行とセルの結合はできない。Typora が保存のときに `|` をそろえるかは、文書になく、未確認。

利用者は、表の形で表示し、原文の中では Tab でセルを移る方針を選んだ。直接編集の型は、保存のたびに原文を書き換えうるので、仕様 §5.2 の「本文に不要な自動の変更を加えない」と合わない。

## Decision

### 1. 表の形で表示する

設定「記号の表示」が既定の「カーソルのある行だけ」（cursorLine）のとき、親が文書（Document）の表（トップレベルの表）を、選択が触れていない間、表の形で表示する。

- 触れていない、とは、選択のどの範囲も、表の範囲に触れないこと。表の範囲は、最初の行の行頭から、最後の行の行末まで。端の一致（表の頭や末尾にカーソルがある）も、触れているとする。触れたら、その表だけが原文に戻る。ほかの表は表示のまま。
- 見出しの行は見出しのセル（th）、本文の行は普通のセル（td）。区切りの行は表示しない。列の配置は、区切りの行の `:` に従う（`:--` 左、`:-:` 中央、`--:` 右、なしは左）。
- 列の数は見出しの行のセルの数。本文の行で足りないセルは空、余るセルは表示しない（GFM と同じ）。空のセルも列に数える。セルの境界は、構文木の行の `|`（TableDelimiter）の位置から求める。構文木の TableCell は、空のセルには出ないため。
- セルの中の `\|` は `|` と表示する。インラインコードの中の `|` も、GFM の仕様どおりセルの区切りになる。
- セルの中の強調、太字、取り消し線、インラインコード、インラインのリンク（文字だけ。リンクの色と下線）、自動リンク `<https://...>`（`<` `>` を除く）、GFM の裸の URL は、ほかの行で記号を隠したときと同じ見た目にする。同じ CSS 変数（`--md-color-link`、`--md-color-code`、`--md-color-muted` など）を使い、e2e で、同じ文書の隠した行と、computed style（太さ、斜体、線、色、フォント、サイズ）が一致することを確かめる。画像、参照リンク、HTML、エスケープ（`\*` など）は、原文の文字のまま。
- DOM は createElement と textContent だけで組み立てる。`innerHTML`、`insertAdjacentHTML` などは使わず、文書に書かれた `<script>` や `<img onerror>` は文字として表示されて、動かない（単体テストと e2e で確かめる。単体テストは、ソースにそれらの API がないことも検査する）。
- 表は内容に合わせた幅。セルには最小幅（6em）があり、本文の幅に入らない表は、表の囲みだけが横にスクロールする（ページは横に動かない。「列幅（Issue #3）」の節）。色は CSS 変数で、明暗のテーマに追従する。
- 原文のまま（これまでと同じ）にするもの: 設定が「常に表示」のとき、素のテキスト（.txt、.text）、引用やリストの中の表、frontmatter の中、構文木の解析がまだ届いていない範囲（表が解析済みの範囲の端に触れているものも含む）。原文の表の中では、ADR-004 の行ごとの記号の隠し方が、今のまま働く。

実装は、表全体を 1 つのブロック（`Decoration.replace` の `block: true`）に置き換える。行をまたぐ置き換えは、CodeMirror では ViewPlugin から出せず、state 側から出す必要があるので、StateField（`tableDisplay.ts`）を使う。表の一覧は、構文木の最上位の子を見るだけで作る。選択だけが変わったときは、触れている表が変わったときにだけ、装飾を作り直す（表の一覧と、表ごとの装飾は使い回す）。原文が同じ表の DOM は、位置がずれても使い回す（`eq`）。

### 2. 表への出入り

- 表示中の表を、修飾キーなしの左クリックすると、クリックしたセルの中身の末尾にカーソルを置く（その結果、表は原文に戻る）。セルの外（枠や余白）なら、一番近いセル。座標から決められなければ、表の頭。⌘/Ctrl+クリックと Alt+クリックも同じ扱いで、リンクは開かない。Shift+クリックは、選択の anchor を保ったまま、head をその位置まで伸ばす。右クリックと中クリックは何もしない。空のセルの行き先は、Tab の移動と同じ（中身の頭）。クリックの transaction は、通常の本文のクリックと同じ `select.pointer` で、本文は変えない（タイプライターモードは、ポインタでの選択では中央へ合わせ直さない。ADR-004 の方針と同じ）。
- 上下の矢印キー（mac は Ctrl-n / Ctrl-p を含む。Shift 付きも）で、表示中の表の上と下の行から表に入る。下へなら見出しの行、上へなら最後の行へ、桁を保って入り、表は原文になる。標準の上下移動は、表示中のブロックを飛ばすので、標準より先に受ける。折り返した行の途中の移動は、標準のまま。
- 左右の矢印キー、検索（一致への移動）、ドラッグ、Undo などで選択が表に触れたときも、表は原文になる。選択が表から出ると、表示に戻る。
- IME の変換中（compositionStarted）は、表示と原文の切り替えを、ほかの表も含めて保留する。変換の開始と終了を state に effect で伝え（終了は、ADR-004 と同じ `AFTER_COMPOSITION_MS` の待ち）、保留中は、表示中の表の位置だけを本文の変化に追従させる。変換中に、ほかの行や表の DOM を作り直さない（e2e で、表の DOM 要素が同一のままであることを確かめる）。

### 3. 本文を変えない

表示の切り替え、出入り、Tab の移動（行を足す最後のセルでの Tab を除く）は、選択だけを変える。docChanged の transaction を出さず、Undo の履歴に何も積まない。保存したバイト列が元と同じこと、コピーした文字列が原文であることを、e2e で確かめる（BOM と CRLF の文書を含む）。

### 4. Tab でセルを移る

設定「記号の表示」によらず（「常に表示」でも）効く。

- 条件: 選択がすべて空で、カーソルがトップレベルの表の中（原文）にあるとき。IME の変換中は、何もしない（キーは受ける）。
- Tab は次のセルの中身の頭、Shift+Tab は前のセルの中身の頭へ、カーソルを移す。区切りの行は飛ばし、行をまたぐ。列の数は、各行の実際のセル（空のセルを含む）で数える。カーソルがセルの中にあれば、そのセルの前後のセル。セルの外（行頭の `|` の前、行末の `|` の後ろ、区切りの行）なら、位置の後ろ（前）で最初（最後）のセル。
- 中身の頭は、セルの左の `|` の後ろの空白を飛ばした位置。空のセルは、左の `|` の直後に空白があれば、その 1 つ後ろ（次の `|` を越えない）。なければ `|` の直後。外側の `|` を書かない行（`a | b`）の最初のセルは、行頭から数える。
- 最初のセルで Shift+Tab は、動かない。キーは受ける（フォーカスは動かさず、文字も入れない）。最後のセルで Tab は、R12 で、表の最後に空の行を足して、その最初のセルへ移るようにした（「入力の支援（R12）」の節）。R11 では、動かずにキーを受けるだけだった。
- Esc の直後の Tab は、表の中でも、これまでどおり本文の外へフォーカスを移す。表の外、範囲を選んでいるとき、引用やリストの中の表は、今の字下げのまま。

Tab は、本体の字下げのキー割り当て（`indentKeymap.ts`）が受ける。Esc の直後の判断をそこに 1 か所で持つため、キー割り当てを部品側に足さず、本体が、Esc の直後でなければ、plugin-api の `tabHandlers`（部品が先に受ける入口）を順に呼び、true を返したものがあれば字下げしない形にした。

### 5. ほかの機能との組み合わせ

- タイプライターモード: 表への出入りも、ほかの選択の移動と同じで、キー操作の後に、カーソルの行が中央に戻る（e2e で、既存のタイプライターの検査と同じ ±6px）。ポインタ（クリック）で入ったときは、中央へ合わせ直さない。
- フォーカスモード: 表示中の表は、カーソルの段落でなければ弱く表示される。行の装飾は、置き換えた表示の中には届かないので、plugin-api に共通の約束を足した。弱く表示する部品（フォーカスモード）は `dimExemptLines`（いま弱くしない行の範囲）を提供し、表示を置き換える部品（Markdown の見た目）は、それを読んで自分の要素に `DIMMED_BLOCK_CLASS` を付ける（見た目の不透明度と遷移は、フォーカスモードが決める）。部品どうしは、互いの内部を import せず、DOM の class を共有もしない（ADR-005 と `architecture.test.ts` の約束）。
- 通常のモード: 表に出入りしたとき、カーソルの行は画面の外へ出ない（e2e で確かめる）。
- 読む位置の保存、アウトライン、検索は、これまでどおり動く（既存の e2e が通る）。

## 列幅（Issue #3）

日本語の短い列が 1〜2 文字の幅に潰れ、縦書きのように見えた。上の「1. 表の形で表示する」の表の幅の規則を、次のように置き換える。

### 原因

CodeMirror は、折り返す本文（`.cm-lineWrapping`）に `word-break: break-word` と `overflow-wrap: anywhere` を付ける（@codemirror/view の baseTheme。Safari が anywhere を持たないため、word-break も付ける）。表の囲みは本文の中にあるので、2 つとも継承され、表のセルでも効いていた。さらに表自身が `overflow-wrap: anywhere` を指定していた。どれも、語の途中でも折れるものとして、列の最小の幅（折り返せる限りの狭さ。min-content）を 1 文字ほどにする。CSS の表の自動レイアウトは、各列の最小の幅と、折り返さないときの幅（max-content）の間で、列の幅を配る。長い文の列が幅を取り、短い列は最小の幅まで縮む。

### 測ったこと

合成の表（Issue の形。見出しは「ブロックタイプ」「役割」「内容」「重要なルール」の 4 列、1 列目はコードの語 `text` `tool_use` `tool_result` `thinking`、ほかは日本語の文）で、列の幅（px）、見出し「ブロックタイプ」の行数、語の途中で折れた語を測った。文字は 18px。本文の列は、窓 600px で 560px、窓 900px で 680px。Playwright の Chromium 156.0.8078.4 と WebKit 27.2（macOS）。変更前は eb5a769。

| 600 | 変更前 | Chromium | 75.5 / 116.5 / 178.5 / 188.5 | 4 | tool_use、tool_result、thinking |
| 600 | 変更後 | Chromium | 140.1 / 137 / 140.7 / 141.3（表の幅 560。本文の幅に入る） | 2 | なし |

### 選んだ規則

- セル（th と td）に `min-width: 6em`。左右の padding（0.7em ずつ）と枠が加わるので、列は約 7.4em（18px で 134.2px）以上になる。
- 折り返しは `word-break: normal` と `overflow-wrap: break-word`。`word-break: normal` で、継承された `word-break: break-word` を打ち消す。日本語の文は、これまでどおり文字の間で折り返す（CJK の文字は、normal でも文字の間で折れる）。長い語や URL は、折らずに、その幅が列の最小の幅になる。
- 表の囲み（`.cm-md-table`）を `overflow-x: auto`、`overflow-y: hidden` にする。表の幅は内容に合わせたまま、最大幅の制限（`max-width: 100%`）を外す。本文の幅に入る表は今と同じ幅で、スクロールバーは出ない。最小幅や長い語を並べても入らない表だけ、囲みの中で横にスクロールする。
- em だけで決めるので、文字の大きさの設定に追従する（16px と 24px で、列の幅を em に直すと同じ。e2e で確認）。色は CSS 変数なので、明暗のテーマに追従する。

値を 6em にした理由。Issue の計画の基準で、`word-break: normal` を足したうえで、6em のまま、Chromium と WebKit の窓 600 と 900 で、見出しが 2 行以内、4 つの語が折れず、4 列の Issue の表が窓 600 でも本文の幅に入ることを確かめた（6.5em と 7em も測った。窓 600 の Chromium で、表の幅が 573.8 と 609.8 になり、囲みが横にスクロールする）。語が折れないのは、`word-break: normal` のとき、語の幅が列の最小の幅になるため。最初の実装は、継承された `word-break: break-word` に気づかず、`tool_result`（コード表示で、Chromium 6.31em、WebKit 6.48em）が 6em で折れたので 7em にしたが、7em はその回避策で、窓 600 の Issue の表を 50px 横にスクロールさせていた。原因を直して 6em に戻した。

`word-break: break-word` が残っていると、`overflow-wrap: break-word` を指定しても、表の自動レイアウトは列の最小の幅を 1 文字ほどに見積もる。このとき、長い URL の表はスクロールせずセルの中で折れ、最小幅を 0 にすると Issue の表が変更前と同じ形に潰れる（Chromium で 78.2 / 122.8 / 190.2 / 167.8 など。レビューでの計測）。`anywhere` に最小幅だけを足した場合との比較は、していない。

### 横スクロールの操作

- トラックパッドの横スクロール（wheel の deltaX）とスクロールバーのドラッグで、表が動く。縦のホイールは、表の上でもエディタが受ける。
- スクロールバーの上の mousedown では、カーソルを動かさず、`preventDefault` もしない（表は表示のまま）。表の囲み自身が押され、押した位置が囲みの下端のスクロールバーの太さ（offsetHeight と clientHeight の差）の中なら、スクロールバーとみなす。
- この判定のため、表のスクロールバーは `::-webkit-scrollbar`（高さ 10px、つまみの色は `--md-color-border`）で、場所を取る型にしてある。macOS 既定のオーバーレイ（場所を取らず、上に重なる）のままだと、スクロールバーの太さが 0 になり、判定できない。
- スクロールした後のセルのクリックは、これまでと同じ（そのセルの中身の末尾）。セルの座標は、スクロール後の位置を使う（`getBoundingClientRect`）。
- 横スクロールバーの分も、囲みの高さに入る。CodeMirror が見るブロックの高さ（`getBoundingClientRect().height`）が、スクロールバーの有無で食い違わない。表の下の行のクリックと、上下の矢印キーの移動は、窓の幅でスクロールバーが出入りしても同じ（e2e で確認）。

### 他のエディタ

親が調べた結果で、私は文書を再確認していない（ネットワークに出ていない）。Obsidian は、表の列の最小幅を CSS 変数 `--table-column-min-width`（6ch）で決め、表の外側を横スクロールにする（https://docs.obsidian.md/Reference/CSS+variables/Editor/Table）。Zettlr は列の min-width が 96px、Joplin は 50px で、どちらも表の外側が `overflow-x: auto`（それぞれのリポジトリのスタイル。ファイルの場所は未確認）。どれも、列の最小幅と、外側の横スクロールの組み合わせ。

### 見送った案

- `word-break: auto-phrase`（日本語の文節で折る）。Chromium 系の機能で、WKWebView で使えるかは未確認。列の最小の幅の問題（短い列が潰れる）は、折る位置では直らない。
- JavaScript で列の幅を計算する。文字の大きさの設定、窓の幅、文書の変更のたびに計算し直す必要があり、描画する前の高さの見積もりも難しくなる。CSS だけで同じ結果が出る。
- 最小幅だけを足し、継承された `word-break: break-word` は残す（最初の実装）。列が潰れるのは防げるが、列の最小の幅が最小幅だけで支えられ、長い URL や長い英字の語は、これまでどおりセルの中で途中から折れて、「入らない表は囲みで横にスクロール」にならない。コードの語も、最小幅より長ければ折れる（`tool_result` は 6em で折れ、7em に上げて回避していた）。採らなかった。

### 限界

- 実機（Tauri の窓、WKWebView）は未確認。Playwright の Chromium と WebKit（macOS）の数字だけ。WebKit では、スクロールバーの操作と wheel は試していない（列の幅と折り返しだけ）。トラックパッドの手触りも未確認。
- 4 列の Issue の形の表は、窓 600px で本文の列（560px）に入る。列が 5 つ以上になる表や、長い URL・長い英字の語を含む表は、囲みが横にスクロールする。長い URL は、折り返さず、セルの幅いっぱいに広がる。
- 最小幅は、セルに `min-width` を付ける形で、CSS 2.1 では表のセルの `min-width` の動きが決まっていない。Chromium と WebKit では効くことを測ったが、ほかのエンジンは未確認。
- 見出しが最小幅で 2 行になるとき、最後の 1 文字だけが 2 行目に残ることがある（「ブロックタイ」「プ」）。
- スクロールバーの判定は、`::-webkit-scrollbar` で場所を取る型にしてあることが前提。この指定が効かなくなると、スクロールバーの上の押下が、カーソルの移動になりうる。
- 横にスクロールした表は、キーボードでスクロールできない（スクロールの手段は、トラックパッドかスクロールバー。クリックや上下の矢印キーで、表は原文になる）。

## 入力の支援（R12）

R11 の実機での確認で、表を書くときの改行とカーソルの支援が求められた。他のエディタの文書を調べ（親が文書を読んだ結果で、アプリは動かしていない）、次の 3 つを選んだ。どれも、利用者がキーを押したときだけ本文を変える（仕様 §5.2。入力中の自動整形はしない）。

### 調べたこと

- Typora: Cmd/Ctrl+Enter で下に空の行を足す。新しい版では Tab でも行を足す。見出しの行を打って Enter で表になる。区切りの行を自動で足すかは、文書では未確認（https://support.typora.io/Table-Editing 、https://support.typora.io/Markdown-Reference/ ）。
- Zettlr 4: Enter で次の行の同じ列へ移り、最後のセルの Tab で行を足す（https://docs.zettlr.com/en/editor/tables/ ）。
- Obsidian の Advanced Tables: Tab で次のセル、Enter で次の行（最後なら行を足す）。`|` と見出しを書いて Tab で表になる（https://GitHub.com/tgrosinger/advanced-tables-obsidian ）。
- Joplin の Rich Tables: 最後のセルの Tab と、最後の行の Enter で行を足す（https://joplinapp.org/plugins/plugin/com.bwat47.rich-tables ）。
- markdown-table-editor: Enter で次の行、Shift+Enter でセル内の改行、行と列の挿入・削除・移動のキー（https://github.com/susisu/markdown-table-editor ）。
- Bear 2: 最後のセルの Enter で行を足す（https://bear.app/faq/how-to-use-tables-in-bear/ ）。

多くが、最後のセルの Tab と、行での Enter で行を足す。見出しの行から表にする操作も、複数ある。Enter での移動（次の行の同じ列）は、Enter が行を足す今回の選択と合わないので採らない。

### 決めたこと

設定「記号の表示」によらず効く。素のテキスト（.txt、.text）、引用やリストの中の表、frontmatter の中、範囲選択、複数の選択、読み取り専用では何もしない（今のまま）。実装は `tableEdit.ts`（何をどこに足し、カーソルをどこに置くかを state だけから求める純関数）と、`tableKeys.ts`（キーへの割り当て）。

1. 表の行での Enter。カーソルがトップレベルの表の中にあるとき、今の行の下に空の行を足し、カーソルをその最初のセルの中身の位置に置く。見出しの行と区切りの行では、区切りの行の下（本文の 1 行目）に足す。カーソルがセルの途中にあっても、文字は分けない（行の末尾に足す）。足す行は、外側の `|` を付け、セルの数は見出しの行のセルの数（GFM の列の数）、各セルは空白 2 つの `|  |  |`。最初のセルの中身の位置は、R11 の「中身の頭」の決まり（空のセルは、左の `|` の直後の空白 1 つの後ろ）と同じで、行頭から 2 文字目。表の最後の行が、セルがすべて空（空白だけ）の本文の行のとき、その行で Enter を押すと、行の文字を消して空の行にし、カーソルをその行に置く（表から出る。リストの継続で、空の項目の Enter がリストを終えるのと同じ考え方）。最後の行でない空の行では、普通に行を足す。
2. 見出しの行での Enter（表を作る）。選択が空で、カーソルが行の末尾（末尾の空白の後ろ）にあり、行が前後の空白を除いて `|` で始まり `|` で終わり、セルが 1 つ以上あり、まだ表でなく、次の行が区切りの行でないとき。行が、親が Document の Paragraph の最後の行のときだけ（構文木で確かめる。コードブロック、HTML ブロック、引用、リスト、frontmatter の中では、普通の改行）。行の後ろに、区切りの行（`| --- | --- |`、数は見出しのセルの数）と、1 の形の空の行を足し、カーソルを空の行の最初のセルの中身の位置に置く。見出しの行の文字は変えない。セルの数え方は R11 の tableModel と同じ GFM の規則（`\|` は区切りにならない。インラインコードの中の `|` は区切りになる）。構文木の Table の中にある行は、1 の表の行として扱う。Paragraph の途中の行（直前に文がある最後の行）でも、lezer の構文木では、表が段落を中断して始まるので、表になる。
3. 最後のセルでの Tab。原文の表の最後の行（本文の行がなければ見出しの行）の最後のセルの中で Tab を押すと、表の最後に空の行（1 と同じ形）を足し、カーソルをその最初のセルの中身の位置に置く。行を足すのは、カーソルがそのセルの中（左の `|` の後ろから右の `|` まで）にあるときだけ。最後の行の末尾の `|` の後ろにカーソルがあるときは、動かずにキーを受ける（R11 と同じ）。Shift+Tab の最初のセル、Esc の直後の Tab（本文の外へフォーカスを移す）、表の外、範囲選択は、今のまま。
4. どれも 1 つの transaction（userEvent は `input`）で、1 回の Undo で、押す前の文書と選択に戻る。
5. 表の外の Enter、リストの継続（tight と preserve）、Shift+Enter、⌘/Ctrl+Enter は、今のまま。リストの継続の Enter（`Prec.highest`）と、表の Enter（同じ `Prec.highest`）は、同時には当てはまらない（表の行と、最上位の段落の行は、リストの項目ではない）ので、順序に依らない。表の Enter が先に並ぶ（`bundledPlugins.test.ts` が並びを確かめる）。
6. Enter で足した行や表は、カーソルが中にあるので原文のまま。表から出ると、R11 の表示に戻る。

### IME の守り

変換中の Enter（keyCode 229、isComposing）と、WebKit で変換の確定の直後に届く Enter の keydown では、行を足さない。守りは、コマンドではなく CodeMirror にある（@codemirror/view 6.43.15 の `InputState.handleEvent` を読んだ）。キー割り当て（keymap）は、view の `keydown` のハンドラとして呼ばれ、その前に `ignoreDuringComposition` が keydown を捨てる。捨てるのは、変換中（`composing > 0`）と、Safari（iOS を除く）で、変換の終了（compositionend）から 100ms 以内で、まだ後続のキーを捨てていないとき（`compositionPendingKey`）。リストの継続の Enter も、同じ経路で守られていて、コマンドの中に IME の判定を持たない。ただし `composing` は、compositionstart の直後はまだ 0 で、DOM の変更を見てから立つ。その間の経路に備え、`tableEnter` と `tableTab` は、`view.composing` と `view.compositionStarted` を見て、変換中は何もせずキーを受ける。確かめたもの: 単体テスト（compositionstart の後に、コマンドを直接呼んでも文書が変わらない）と、e2e（CDP の変換の模擬で、keyCode 229 の Enter では行が増えず、確定後の Enter で増える）。e2e は、コマンドの判定を外しても通った（CodeMirror の捨てる経路で守られているため）。WebKit の確定の直後の Enter は、Chromium では再現できず、コードを読んだだけで、実機は未確認。

### やらないこと（R12）

入力中の列の自動整形、`|` をそろえるコマンド、行と列の移動や削除のキー、Shift+Enter でのセル内の改行、今いるセルと列の強調、新しい設定項目、引用やリストの中の表への支援。

## やらないこと

セルへの直接の書き込み、入力中の自動整形と `|` をそろえるコマンド、列幅の調整（利用者が列の幅を変えること。列幅の既定の規則は「列幅（Issue #3）」）、行や列のドラッグ、並べ替え、セル内の改行、セルの結合、表示中の表のリンクの ⌘/Ctrl+クリックで開くこと、行を足すキー操作のうち「入力の支援（R12）」で決めたもの以外（行や列の移動と削除など）、新しい設定項目（表示は、既存の「記号の表示」に従う）。

## Consequences

- 既定の見た目が変わる。表を原文で見たい利用者は、設定で「常に表示」にする（表のセルの移動の Tab は、そのままできる）。
- 部品の拡張のうち、Markdown の見た目が、StateField と、本体への入口（`tabHandlers`）を使うようになった。plugin-api に、`tabHandlers`、`dimExemptLines`、`isDimmedBlock`、`DIMMED_BLOCK_CLASS` が増えた。
- 性能（Chromium、Apple M5 の macOS、メモリ bridge の e2e ビルド。変更前は d534236。ビルドごとに新しいページで、交互に 5 ラウンド、各 100 回）: 表 200 個（各 20 行、3 列。4602 行）の文書で、キーを押してから CodeMirror の更新通知までの中央値は、カーソルの下への移動 0.7ms（変更前 0.7ms）、上への移動 0.7ms（0.7ms）、表の外での 1 文字の入力 1.1ms（0.9ms）、表の中での 1 文字の入力 0.9ms（0.9ms）。表のない約 1MB（35086 行）の文書の 1 文字の入力は 2.4ms（2.3ms）。doc の変更のたびに表の一覧を作り直すが、構文木の最上位を配列のまま読むので、表のない長い文書でも、ほとんど増えない（ノードの参照を作る走査では、1MB の入力が 2.5ms から 3.2ms に増えたので、この形にした）。

## 限界

- 実機（Tauri の窓、WKWebView）と、実 IME（Microsoft IME、macOS の日本語入力、Mozc）では、未確認。Playwright の Chromium と、CDP による変換の模擬だけで確かめた。Windows と Ubuntu の実機も未確認。
- 表に出入りすると、表の高さが変わり、下の行が動く。表示中の表と原文の高さは、一致しない。描画する前の表の高さは見積もりで、実際の高さと違うため、遠くへのスクロール中に、スクロールバーの長さが少し変わることがある。
- 表示中の表は、中の文字を選んだり、一部だけコピーしたりできない（クリックすると原文になるので、原文で選ぶ）。検索の一致の強調は、表示中の表の中には出ない（一致に移ると原文になる）。
- クリックで置かれるカーソルは、クリックした文字の位置ではなく、そのセルの中身の末尾。
- 引用やリストの中の表、frontmatter の中は、表示しない。インラインコードの中の `|` は、GFM の仕様どおりセルの区切りになるので、そのセルは、コードとして表示されない（原文の文字のまま）。
- 構文木の解析が追いついていない範囲の表は、原文のまま。長い文書で、解析が届くと表示に変わる。
- 画像、参照リンク、HTML は、表示中の表の中でも原文の文字のまま。
- 表示中の表のスクリーンリーダーでの読み上げ（th と td の構造は、素の table 要素）は、確かめていない。

## 判断を見直す条件

- 実機（WKWebView）や実 IME で、表の出入りや変換中の表示に問題が出たとき。
- 表の中のセルを、表示のまま編集したい要望が出たとき（直接の編集は、本文の自動変更を伴いうるので、仕様 §5.2 の見直しとあわせて決める）。
- 行や列の移動と削除のキー、`|` をそろえるコマンドの要望が出たとき（Zettlr、VS Code の拡張の型）。
- 引用やリストの中の表を、表示したい要望が出たとき。
- 表に出入りしたときの高さの変化が、日常の使い方で気になるとき。
