# 保存の信頼性（Phase 2 前半）

仕様書 §6 の FS-02、FS-04、FS-05、FS-06、FS-07 と、受入基準 4（外部編集と未保存変更の衝突で、無言の上書きが起きない）、受入基準 5（強制終了の模擬後に草稿を復旧できる）の実装方針。コードの置き場所は末尾の表。

## revision と保存直前の検査（FS-04）

- revision は、ディスク上のバイト列の SHA-256（16 進、小文字 64 桁）。`open_document`、`save_document`、`save_document_as`、`check_document` が返す。mtime やサイズは使わない。
- 文書は、最後に読み込んだ・保存したときの revision を `diskRevision` として持つ。ファイルがない前提（新規文書、削除された文書）は null。
- `save_document` は、書く直前にディスクの現在の内容のハッシュを取り、`expectedRevision` と違えば書かずに conflict を返す。conflict には、現在のディスクの状態（present と revision、または missing）が入る。
- ディスクの内容が、これから書く内容と同一なら、期待と違っていても衝突にしない（何も失われない）。書き込まず、unchanged を返す。

### 競合窓

比較から rename までの間に、別のプロセスが同じファイルへ書く可能性は残る。ファイルシステムに、比較と置き換えを不可分に行う操作がないため。この窓は、ハッシュ計算と一時ファイルの書き込み・fsync にかかる時間（通常の文書ではミリ秒単位）に限られる。窓の中で書かれた内容は、rename で置き換わる。上書きを選んだとき以外は、検査を通った直後の変更だけがこの窓で失われうる。窓を閉じるにはファイルロックが要るが、他のエディタやエージェントが従うとは限らないため採らない。

## 外部変更の検知（FS-05）

- Rust の notify で、開いている文書の親ディレクトリを監視する。ほかのエディタの多くが一時ファイルへ書いてから rename で置き換えるため、ファイル自体は監視しない。対象ファイルに関するイベントだけを選び、200ms 静かになるまで（最大 1 秒）まとめて、`document-changed` イベントを UI に送る。シンボリックリンクの文書は、実体のディレクトリも監視する。
- イベントは「変わったかもしれない」だけを伝える。UI が `check_document` で revision を比べて判断する。自分の保存で起きた変更は、revision が `diskRevision` と一致するので何も起きない。
- ウィンドウがフォーカスを取り戻したときにも `check_document` で確かめる（監視の取りこぼし対策）。
- 状態は、`DocumentState` とは別の型付きの状態（none、changed、deleted、conflict）で持ち、遷移は純関数（`src/document/external.ts`）で表す。

| 状況 | 動作 |
|---|---|
| 未保存の変更なし、内容が変わった | 自動で読み直し、通知する |
| 未保存の変更あり、内容が変わった | 本文に触れず、競合バーを出す |
| ファイルが削除された | 本文と未保存状態を残して通知する。保存すると、確認のうえ作り直す |
| 保存直前の検査で conflict | 書かずに、競合バーを出す |

競合バーの選択肢は、差分を見る（`@codemirror/merge` で自分の本文とディスクの内容を並べる）、ディスクから読み直す（自分の本文を新しい草稿として退避してから読み込む。退避先を通知する）、自分の版を残す（次の保存で `overwrite=true`）の 3 つ。

## バックアップ（FS-07）

`overwrite=true` で、ディスクの内容が期待と違うとき、書く前に現在のディスクの内容をアプリのデータ領域の `backups/` に保存する。ファイル名は「元のファイル名.時刻（UTC）.revision の先頭 8 桁.bak」。バックアップに失敗したら書かない。全体で最大 50 ファイル・100 MiB を保持し、超えたら古い順に消す（直前に作ったものは消さない）。

## 草稿（FS-02、FS-06）

- 草稿は、文書ごとの JSON（draftId、path、text、format、baseRevision、updatedAt）で、アプリのデータ領域の `drafts/` に原子的に書く。元の文書には書かない。draftId は UUID の形式だけを受け付け、ファイル名に使う。
- 未保存の変更がある間、入力が 2 秒止まったら書く。保存・読み直し・破棄・文書の切り替えで未保存の変更がなくなったら消す。
- 起動時に草稿があれば、文書名と時刻を出して、復元する・破棄する・あとで を選ばせる。複数あるときは最も新しいものを出し、ほかの件数を知らせる（選択は出した 1 件にだけ効く）。
- 復元時、元のファイルの revision が草稿の baseRevision と違えば、競合として扱う。元のファイルが読めなければ、保存先のない文書として復元する。
- 草稿がなければ、`session.json`（前回開いていた文書のパス。Preferences とは別）の文書を開き直す。ファイルがなければ何もしない。無題の文書に切り替えた（新規）ときは、この記録を消す（次回の起動で前の文書を開き直さない）。
- 強制終了の直前 2 秒以内の入力は、草稿に入らない。

## 終了時の確認（FS-02）

窓の閉じる操作（`CloseRequested`）と、窓を閉じない終了要求（macOS の Cmd+Q など、`ExitRequested`）を Rust で止め、UI に `close-requested` を送る。UI は、未保存の変更がなければそのまま `close_app` を呼ぶ。あれば 保存 / 保存しない / キャンセル を確認する。保存しない場合は、その文書の草稿も消す。UI が最初の描画を終える前は、確認の相手がいないので止めない。ほかの操作（フォーカス時の外部変更の確認など）の実行中に閉じる要求が届いたときは、捨てずに、その操作が終わった後に処理する。確認ダイアログの表示中に届いた二重の要求は捨てる。

## シンボリックリンクとネットワークドライブ

- 保存先がシンボリックリンクなら、リンク先の実体に原子的に保存し、リンクは残す。この挙動は、保存の実装（`crates/docio/src/save.rs`）が元から備えていたもので、`docio` と `src-tauri` のテストで固定した。保存前の revision の確認と外部変更の確認は、リンク先の実体の内容に対して行う。リンク切れは、ファイルがない（削除された）扱い。
- ネットワークドライブは特別扱いしない。ローカルのファイルと同じ経路で読み書きする。ネットワークドライブでは、ファイル監視のイベントが届かない、または遅れることがある。その場合でも、保存直前の検査とフォーカス復帰時の確認が、外部変更を検出する。検証していない（下の「未検証」）。

## コードの置き場所

| 役割 | 場所 |
|---|---|
| revision、保存直前の検査、バックアップ | `crates/docio`（`revision.rs`、`checked.rs`、`backup.rs`） |
| 草稿、セッション、監視、Tauri コマンド | `src-tauri/src`（`drafts.rs`、`session.rs`、`watcher.rs`、`documents.rs`、`lib.rs`） |
| 外部変更の状態遷移、復旧の判断 | `src/document/external.ts`、`src/document/recovery.ts`（純関数） |
| 草稿の自動保存（debounce） | `src/document/drafts.ts` |
| 副作用の順序 | `src/document/controller.ts` |
| e2e 用のメモリ実装 | `src/platform/memory/memoryBridge.ts` |

## 未検証

- Windows と Ubuntu 実機での、ファイル監視の挙動（置き換え保存のイベント、遅延）。
- ネットワークドライブ（SMB、NFS など）での監視、rename の原子性、シンボリックリンク。
- ディスクフルなど、保存の失敗系の実機での再現。
- 大きな文書（1 MiB 以上）での、2 秒ごとの草稿の書き込みの負荷（性能試験は Phase 2 後半）。
