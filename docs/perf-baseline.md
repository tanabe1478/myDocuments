# 性能の基準値

仕様 §9.1 の項目を、毎回同じ手順で計測・記録・比較する仕組み（perf/）の基準値。macOS（Apple Silicon）の実機で、同じコミットから 2 回通した値を基準にする。表の「a / b」は 1 回目 / 2 回目。

- 現在の基準値は B0（部品化の前の準備）。コミット 1df73d1 から 2 回。生データは perf/results/20261103-1df73d1.json（1 回目）と perf/results/20261103-1df73d1-2.json（2 回目）。
- 前の基準値は Run 7.1。コミット 6cff26e から 2 回。生データは perf/results/20261101-6cff26e.json と -2.json。記録は「前の基準値（Run 7.1）の記録」の節に残してある。
- Run 7 の最初の基準値（perf/results/20261101-869dfd7.json と -2.json）は、標本（samples）を持たない古い形式のまま残してある。
- 引数なしの perf:compare は、perf/results/ のうち結果 JSON の generatedAt（計測した時刻）が新しい 2 件を比べる。今は B0 の 2 件なので、引数なしだと B0 の 1 回目と 2 回目の比較になる。次の計測を perf/results/ に足すと、引数なしの比較は「B0 の 2 回目」と「その新しい結果」になる。基準値（2 回の組）どうしを比べるときは、ファイルを引数で指定する。

## 現在の基準値（B0、コミット 1df73d1）

### 結論

- 仮目標（仕様 §9.2）は、測れた範囲で満たしている。通常文章（A、B）の入力から描画までの p95（95 パーセンタイル。遅い方から 5% 目の値）は、chromium 20.2ms 以下、webkit 18ms 以下で、50ms を下回る。100KB（B）を開く操作は Web UI で中央値 chromium 9.5〜9.9ms、webkit 12〜19ms。
- 入力の処理時間（フレームに丸められない）は、A、B で chromium 1.0〜1.6ms、webkit 2〜4ms（中央値）。C、D（1MB 前後）は chromium 2.8〜5.3ms、webkit 4〜7ms。
- 100KB を開く操作の仮目標（1 秒以内）は、Run 7.1 と同じく Tauri 実機のファイル選択ダイアログを含む経路では測れていない（Web UI のメモリ bridge までと、docio の読み込み・復号）。
- Tauri release の起動は、窓が出るまで warm で中央値 492.4ms と 426.4ms、cold は 1025.8ms と 1152.8ms（各 1 回）。Run 7.1 の warm（389ms、384.5ms）より、2 回の平均で 18.8% 遅い（前回の文書ありの起動は +17〜23%）。ただし今回の計測は開始時の load average（直近 1 分の実行待ちプロセスの平均数）が 7.6 と 8.1 で、Run 7.1 の 3.8 と 4.7 より高かった。負荷の影響とコードの影響は分けられていない（「前の基準値（Run 7.1）との比較」の節）。
- 常駐メモリは全プロセス合計で、空 212〜215MiB、100KB 229〜239MiB、1MB 206〜209MiB。1MB が空とほぼ同じ値になったのは Run 7.1（248〜249MiB）と合わない。標本の値が 2 つの山（約 250MiB と約 200MiB）に分かれている（原因は未確認。下記）。
- 配布物は release の実行ファイル 3.70MiB（3,883,168 バイト）、.app 3.75MiB（3,934,091 バイト）、dist/ 0.88MiB（927,678 バイト）。Run 7.1 より実行ファイルが +182,352 バイト（+4.9%）、dist/ が +54,496 バイト（+6.2%）。
- B0 の 2 件を perf:compare に渡すと exit 0（悪化 0 件）。

### 項目ごとの変化（2 回の平均どうし）

perf:compare の判定とは別に、中央値の「Run 7.1 の 2 回の平均」と「B0 の 2 回の平均」を比べた。全 116 項目のうち、次の両方を満たす項目を載せる。

- 変化が 20% 以上。
- Run 7.1 の 2 回の値と B0 の 2 回の値が重ならない（B0 の最小が Run 7.1 の最大より大きい、またはその逆）。

例外として、Tauri の起動（warm、前回の文書 C あり）、サイズ、メモリ（空の文書、1MB）は、20% 未満でも代表として載せる。

これは判定の式ではなく、2 回ずつの値の見取り図。残りの項目は、2 回の範囲が重なる（62 件）か、重ならなくても変化が 20% 未満（36 件）。重ならず 20% 以上だったものは、悪化方向が 2 件（Tauri 起動の cold と、前回の文書 B ありの起動）、改善方向が 16 件。

## 悪化の判定（perf:compare、Run 7.1）

式と係数は perf/lib/judge.mjs の冒頭と perf/compare.mjs の冒頭のコメントにもある。中央値と p95 のそれぞれで、次の 3 つをすべて満たしたときだけ悪化とする。

- 悪化方向に 20% 以上動いた（既定。--threshold で変える）。
- 差が、標本の揺れの K 倍を超える。K は 3（--sigma で変える）。標本が 20 件未満のときは、揺れの推定自体が不安定なので 3 × sqrt(20 / n) に大きくする（n = 15 で 3.5、10 で 4.2、5 で 6、3 で 7.7。n は base と new の小さいほう）。
- 差が、単位ごとの小さな下限以上。ms は 2（webkit の performance.now が 1ms 刻み）、MiB は 2、bytes は 4096、docio は 0.002ms（Rust の計時は ns 精度で 1 回が 1ms 未満）。Web UI のフレームに量子化された遅延（入力から描画まで、IME、開く、モード、スクロール）の p95 だけは 17ms（60Hz の 1 フレーム）。中央値には下限の 17ms や 10ms を掛けない（Run 7 は中央値 10ms、p95 17ms だった）。

揺れ（noise）は、標本（結果 JSON の samples）から、base と new のそれぞれで次の 2 つの大きいほうを求め、さらに base と new の大きいほうを使う。

- 1.4826 × MAD（中央絶対偏差。正規分布なら標準偏差に一致する）。標本の中心の幅。
- ブロックブートストラップの標準偏差。標本を、実行順に連続した ceil(sqrt(n)) 件のブロックごとに復元抽出し直して（400 回、固定シード）、その統計量（中央値または p95）を求め直したときのばらつき。MAD は分布の中心の幅しか見ないので、二峰の分布（IME の確定は 0〜3ms と約 16ms の 2 つの山で、中央値がどちらに落ちるかで 3ms と 15ms の間を動く）や、遅い反復が時間的に固まって出る分布のぶれを過小評価する。

そのほかの扱い。

- 標本が 3 件未満の項目（cold）は判定しない。比較結果の「参考（判定対象外）」に別に出す。
- p95 は、base と new の標本がどちらも 40 件以上のときだけ比べる（Run 7 は 20 件。20 件だと p95 が上から 2 番目の値になる）。
- p95 の悪化は、同じ項目の中央値も悪化と判定されたときだけ悪化に数える。中央値が動かない p95 だけの悪化は「p95 だけの悪化」として別に出し、exit には効かせない。理由: 同じコードの 2 回で、中央値は動かないのに p95 が 50〜180% 動いた項目が 6 件あった（docio の C の 4 項目と webkit の入力の処理時間 2 項目）。遅い反復は OS の負荷で時間的に固まって出て、その量が 1 回ごとに違う（decode C は、1 回目は遅い反復が 200 件中 12 件、2 回目は約 70 件）。1 回の標本の中からはこの回間の違いを推定できず、MAD もブロックブートストラップも足りなかった。限界: 裾だけが悪化して中央値が動かない変更は、exit では検出できない（出力には残る）。
- 標本が無い古い結果 JSON（Run 7 の 2 件の docio など）との比較は、従来の固定の下限（Web UI の遅延は中央値 10ms、p95 17ms、docio 0.5ms など）で判定する。加えて、結果に残っている p95 と中央値から裾の広さ (p95 - 中央値) / 1.645 を揺れの代用にして、差がその K 倍を超えることも求める。比較の出力に「従来の固定の下限で判定した項目」として件数を出す。新しい結果でも、スクロール（フレーム時間の要約だけ）はこの扱いになる。
- 配布物のバイト数とスクロールの引っ掛かり回数（frames）は、揺れの無い決定的な値として、割合と下限だけで判定する。
- 環境（CPU、OS、ブラウザの版、WKWebView の版）や条件（quick か、--inject-input-delay の値）が違うと、警告を出す。

### 判定の変更の根拠（同じコードの 2 回）

- Run 7 の判定（固定の下限）は、Run 7 の古い 2 件（同じコード）で 3 件を悪化とし exit 1 だった（docio.revision.D の中央値 +59.8% と p95 +21.2%、cold +20.0%）。新しい判定では、cold は参考に回り、docio.revision.D は 1 回目だけが速かった外れ値で、計測内の広がり（p95 - 中央値）が差より大きいので無視され、exit 0。比較した値は 153 で、従来の下限で判定した項目は 30 件（標本が無いもの）。
- 新しい 2 件では、比較した値は 185。悪化 0、p95 だけの悪化 6、参考 1（cold、-24.9%）、揺れの範囲か下限未満で無視 42、改善 3。exit 0。
- 判定の変更の途中経過: 標本の MAD だけで判定すると、新しい 2 件で 6 件（IME 確定 D 末尾の中央値 3 → 15.1ms を含む）が悪化として出た。IME の確定はブートストラップで解消した。残りの p95 の 5 件は、上の「p95 だけ」の扱いにした。
- quick（回数が少ない）どうしでも、遅延なしなら exit 0 になるよう、標本が少ないときの K の拡大と、quick の入力を 15 回から 40 回にする変更を入れた。それまでは、遅延なしの quick どうしで mode（3 件の標本、MAD が 0）や IME 確定（5 件）が悪化と出ていた。
- docio の回数: Run 7 の基準値は既に 50 回（暖機を除く）だった。1 回が 1ms 未満で、50 回では中央値が 2 回で +20〜60% 動いたので、200 回にした（全体の所要時間は 355 秒から 365〜370 秒）。200 回にしても、docio の D は中央値が回ごとに最大 2 倍動く（上の表）。1 回の計測の中の二峰と時間的な固まりがあるためで、判定は上の揺れ（ブートストラップ）に任せる。docio だけを 2 回走らせて比べる（--only docio）と exit 0。

## 検出の確認（遅延の注入）

計測専用のオプション --inject-input-delay <ms> は、計測側のページ注入で、全ての keydown の最初（document の capture）に、指定した ms のビジーウェイトを足す。アプリのコード（src/）は変えず、本番のビルドにも含まれない。遅延を注入した結果は perf/out/ にだけ出し、perf/results/ には置けない（--out で perf/results/ を指すとエラー）。結果 JSON の mode.injectInputDelayMs に値を残す。遅延は keydown の timeStamp より後に入るので、入力から描画までと入力の処理時間のどちらにも含まれる。Mod+O やモード切替のショートカットも keydown なので、開く操作とモード切替にも効く。

確認の結果（quick、--web-only、同じコミット、同じマシン）。

| 比べたもの | exit | 結果 |
| --- | --- | --- |
| 遅延なしの quick 2 件（q1 と q2。両方向） | 0 | 悪化なし |
| 基準値（6cff26e-2、フル）と、遅延なしの quick | 0 | 悪化なし |
| 遅延なしの quick（q1）と、遅延 3ms の quick | 1 | 悪化 13 件。入力の処理時間（chromium）が 10 件。例: A 中央 1.4 → 4.2ms（+200%）、C 末尾 4.4 → 7.3ms（+66%）。モード切替の chromium が 2 件、IME 確定が 1 件（下記） |
| 遅延なしの quick（q2）と、遅延 3ms の quick | 1 | 悪化 9 件。入力の処理時間（chromium）が 5 件（A 末尾 1.3 → 3.8ms、D 中央 2.8 → 5.9ms など）、モード切替の chromium が 4 件 |
| 基準値（6cff26e-2、フル）と、遅延 3ms の quick | 1 | 悪化 9 件。入力の処理時間（chromium）が 5 件、モード切替が 4 件。quick とフルの回数の違いの警告つき |
| 遅延なしの webkit quick と、遅延 10ms の webkit quick | 1 | webkit の入力の処理時間が悪化。例: A 中央 3 → 11ms |

限界。

- webkit は 1ms 刻みの計時で標本の揺れが 1.5ms 前後あり、3ms の注入（処理時間が 1〜2ms から 4ms）は、quick の回数では揺れの 3 倍を超えず検出されなかった。10ms なら検出される。
- 遅延 3ms と q1 の比較で、IME 確定（chromium B 中央）の中央値 1.4 → 15.4ms も悪化として出た（q2 と基準値との比較では出ていない）。IME は keydown を使わないので注入の影響ではなく、quick の標本 5 件の二峰による偽陽性。標本が少ない quick は、検出の確認とスモークに使い、判定の根拠にはフルの結果を使う。
- 入力から描画まで（フレーム単位）の chromium B 末尾の中央値 7.1 → 18.3ms は、遅延 3ms の比較では「揺れの範囲」として無視された（二峰の分布で揺れが大きい）。入力の処理時間の指標のほうが検出に向く。

結果 JSON とログは perf/out/（gitignore）に出た。比較の出力は evidence に保存した。

## 揺れ（同じ環境の 2 回の差）の読み方（Run 7.1 の 2 件。B0 の 2 件の揺れは「新しい 2 件の比較」）

- 揺れが小さい項目: Tauri の warm 起動（中央値の差 -1.2%）、メモリ（差 0.6〜1.0MiB）、docio の save_atomic（内容が変わる。-0.9%〜+1.6%）、スクロールのフレーム時間（差 0）、配布物のサイズ（差 0）、chromium の入力の処理時間（A、B で差 0.3ms 以内）。
- 揺れが大きい項目: cold（1 件。-25%）、webkit の入力から描画まで（D 末尾の中央値 6 → 13ms など。二峰）、docio の D（上記）、IME 確定。
- 判定の限界: Web UI の遅延は 60Hz のフレームに量子化され、二峰の分布になる。標本の揺れが大きい項目の小さな悪化は検出できない（揺れの 3 倍を超えるまで）。p95 だけが悪化する変更は exit では検出できない（上記）。
- 同じ環境で比べる。環境（CPU、OS、ブラウザ、WKWebView の版、電源）が違うと compare は警告を出す。
- 悪化が出たら、もう一度計測して再現するかを見る。

## 測り方

- 入力から描画まで: Playwright で文字 a を 1 つずつ押す。keydown（キャプチャ段階）の timeStamp から、本文が変わり（編集エンジンの onChange）、その次の描画フレーム（requestAnimationFrame の後の最初のタスク）の後までの時間。押下ごとに描画の観測を待ってから次を押し、間に 25ms 空ける。最初の 10 回は暖機として捨てる。本文の増加が送った数と一致することを確認する。
- 入力の処理時間: 上と同じ keydown の timeStamp から、onChange（CodeMirror の update listener。本文の DOM の更新が済んだ後に呼ばれる）が呼ばれた直後（マイクロタスク）の performance.now まで。requestAnimationFrame も MessageChannel も待たないので、60Hz のフレームには丸められない。計測側のページ注入（perf/lib/inpage.mjs）だけで行い、アプリのコードは変えない。
- IME: chromium の CDP の Input.imeSetComposition で変換中の文字列を更新し、最後に Input.insertText で確定する。更新は compositionupdate から本文の反映と次の描画後まで、確定は compositionend から、確定した文字が本文にある次の描画後まで。確定する文字は 1 回ごとに別の文字（CJK 拡張 A）にして、本文に同じ文字列が残っていて待たずに成立するのを避ける。
- スクロール: scrollTop を requestAnimationFrame ごとに一定速度（2,400px/秒）で進め、フレームの間隔を記録する。最初の 1 秒は暖機。
- 開く操作: メモリ bridge の openPath に仮想パスを渡して Mod+O を押す。keydown から、doc-title と先頭行が期待どおりになった次のフレームの後まで。毎回、小さい文書を挟んで別の文書へ切り替える形にする。
- モード切替: Mod+Shift+F（フォーカス）と Mod+Shift+T（タイプライター）の keydown から、DOM の状態（.cm-md-dim、.cm-typewriter と余白の CSS 変数）が変わった次のフレームの後まで。
- docio: 標準ライブラリだけで時間を測る example（cargo run --release、200 回）。内容が毎回変わるよう、末尾の改行を足す、外すを交互にする。反復ごとの値（samples）を出す。
- Tauri: HOME と CFFIXED_USER_HOME を計測用のディレクトリ（perf/out/tauri-runs/）へ向けて起動する。前回の文書（session.json）に fixture のパスを置いて、起動時に開き直させる。窓の出現は CGWindowList（Accessibility 権限不要）で観測し、OS へのキー入力・マウス操作は送らない。メモリは ps の rss を、アプリ本体と、起動前に無かった com.apple.WebKit.WebContent、GPU、Networking の合計とする。実ユーザーの Library の既知の場所の署名（サイズと mtime）を前後で比べ、変化があれば結果に失敗として残す。
- p50、p95 は nearest-rank の分位点。

## 再現コマンド

```
npm ci --registry https://registry.npmjs.org
npx playwright install chromium webkit      # 公開 npm を使う
npm run perf                                # 全部（macOS 実機、約 6 分）→ perf/results/<日付>-<コミット>.json
npm run perf -- --quick --web-only          # 回数を減らした Web UI だけ（約 1.6 分）→ perf/out/（gitignore）
npm run perf -- --quick --web-only --inject-input-delay 3   # 計測専用の遅延注入（検出の確認。結果は perf/out/）
npm run perf:compare                        # perf/results/ のうち generatedAt が新しい 2 件を比べる（古い方が base）。悪化があれば exit 1
npm run perf:compare -- <base.json> <new.json>
npm run perf:test                           # 判定の仕組みの単体テスト（node:test）
```

オプションは perf/run.mjs の冒頭を参照（--only web,docio,size,tauri、--browsers、--skip-build、--with-debug、--inject-input-delay）。測定中は、同じマシンで重い処理（cargo、npm run test:e2e など）を並行して走らせない。CI では計測しない。

## 未計測

- Windows と Ubuntu の実機。
- 実 IME（macOS の日本語入力、Microsoft IME、Mozc）。IME は chromium の CDP の模擬だけで、webkit は未計測。
- Tauri 実機のキー入力から描画まで、スクロール、モード切替、ネイティブのダイアログを通した開く操作と保存（OS へ入力を送らない方針）。Web UI の値は WKWebView の値ではない（Playwright の webkit は別ビルド）。入力の処理時間の指標も Web UI（メモリ bridge）の上で、Tauri 実機では未計測。
- Tauri の「編集可能」の厳密な定義。窓の出現を代用した。
- cold の厳密な条件。ビルド直後の最初の 1 回だけで、OS のキャッシュ状態（再起動直後など）は制御していない。標本は 1 件で、判定には使わない。
- スクロールのフレーム時間の標本（結果 JSON には要約だけを持つので、揺れによる判定ができない）。
- p95 だけが悪化する変更の自動検出（中央値が動かない場合は exit に効かない）。
- 遅延注入の webkit での 3ms の検出（1ms 刻みの計時と揺れのため、quick では検出されなかった）。
- debug ビルドの起動時間（--with-debug で取れるが、この基準値では取っていない）。
- 保存後の fsync の影響を除いた値、ファイルがキャッシュに無い読み込み。
- 依存コンポーネントの一覧（仕様 §9.1 のパッケージサイズと依存コンポーネントのうち、依存は docs/licensing-audit.md を参照）。
