# 性能の基準値（Run 7）

仕様 §9.1 の項目を、毎回同じ手順で計測・記録・比較する仕組み（perf/）の最初の基準値。macOS（Apple Silicon）の実機で、同じコミットから 2 回通した。生データは perf/results/20261101-869dfd7.json（1 回目）と perf/results/20261101-869dfd7-2.json（2 回目）。表の「a / b」は 1 回目 / 2 回目。

## 結論

- 仮目標（仕様 §9.2）は、測れた範囲で満たしている。通常文章（A、B）の入力から描画までの p95 は、chromium 20.3ms 以下、webkit 19ms 以下で、50ms を下回る。100KB（B）を開く操作は Web UI で 11〜16ms（中央値）。
- ただし 100KB を開く操作の仮目標（1 秒以内）は、Tauri 実機のファイル選択ダイアログを含む経路では測れていない。測れたのは Web UI（メモリ bridge）の本文表示までと、docio の読み込み・復号（B で 0.3ms 前後）。
- 1MB（C）と D は、入力の中央値が chromium で 17〜19ms に上がる（A、B は 6〜7ms）。p95 は 24.2ms 以下で、仮目標の範囲内。
- Tauri release の起動は、窓が出るまで warm で中央値 386〜406ms、cold は 742〜890ms（各 1 回）。常駐メモリは全プロセス合計で、空 208MiB、100KB 237MiB、1MB 248〜250MiB。
- 配布物は release の実行ファイル 3.53MiB（3,700,816 バイト）、.app 3.58MiB（3,751,739 バイト）。
- 同じコードの 2 回で、perf:compare は 3 件を 20% 以上の悪化として報告した（下記「揺れ」）。いずれもコードの変更ではなく計測の揺れで、再計測で確かめた。

## 揺れ（同じ環境の 2 回の差）

perf:compare の実行結果は evidence に保存した。比較した値は 162（中央値と p95。p95 は標本 20 件以上のみ）。

- 20% 以上悪化と報告されたのは 3 件。
  - docio.revision.D の中央値（1.3 → 2.0776ms、+59.8%）と p95（+21.2%）。1 回目が外れ値だった。同じ docio の計測をさらに 2 回、単独で走らせると 2.061、2.073ms で、2 回目と一致した（C は 1.84、1.86ms、decode.D は 1.23、1.26ms）。つまり 1 回目が速く、コードの変更ではない。
  - tauri.startup.release.cold の中央値（741.5 → 890.1ms、+20.0%）。cold は標本が 1 件で、OS のキャッシュ状態を制御していないので、揺れが大きい。cold は 1 回ごとの値として読み、20% 超でも、再計測で再現するまで悪化とは判断しない。
- 割合は 20% を超えたが、絶対差が下限未満で無視された値は 23 件。ほとんどは Web UI の遅延（1 フレーム未満の差）と、docio の 0.5ms 未満の差。
- 20% 以上改善と報告されたのは 5 件で、いずれも Web UI の IME（更新、確定）と docio の save_atomic（同じ内容）の p95。
- 揺れが小さい項目: Tauri の warm 起動（中央値 -5%）、メモリ（差 0.3〜2.1MiB）、docio の save_atomic（内容が変わる。-1.8%〜-0.2%）、スクロールのフレーム時間（差 0）、配布物のサイズ（差 0）。
- 悪化の検出の確認: 1 回目の結果を加工した合成の結果（入力 B 末尾を中央値 4 倍、p95 3 倍、C のメモリ +30%、実行ファイル +25%）を比べると、4 件が悪化として出て exit 1。

読み方の限界:

- Web UI の遅延は 60Hz のフレームに量子化される。中央値の差が 10ms 未満、p95 の差が 17ms 未満は無視する（compare.mjs の下限）。この下限未満の悪化は検出できない。例: 入力 B 末尾の中央値が 7.1ms から 10.6ms（+50%）になっても報告されない。
- 同じ環境で比べる。環境（CPU、OS、ブラウザ、WKWebView の版、電源）が違うと compare は警告を出す。
- 悪化が出たら、もう一度計測して再現するかを見る（compare の出力にも書いた）。

## 測り方

- 入力から描画まで: Playwright で文字 a を 1 つずつ押す。keydown（キャプチャ段階）の timeStamp から、本文が変わり（編集エンジンの onChange）、その次の描画フレーム（requestAnimationFrame の後の最初のタスク）の後までの時間。押下ごとに描画の観測を待ってから次を押し、間に 25ms 空ける。最初の 10 回は暖機として捨てる。本文の増加が送った数と一致することを確認する。
- IME: chromium の CDP の Input.imeSetComposition で変換中の文字列を更新し、最後に Input.insertText で確定する。更新は compositionupdate から本文の反映と次の描画後まで、確定は compositionend から、確定した文字が本文にある次の描画後まで。確定する文字は 1 回ごとに別の文字（CJK 拡張 A）にして、本文に同じ文字列が残っていて待たずに成立するのを避ける。
- スクロール: scrollTop を requestAnimationFrame ごとに一定速度（2,400px/秒）で進め、フレームの間隔を記録する。最初の 1 秒は暖機。
- 開く操作: メモリ bridge の openPath に仮想パスを渡して Mod+O を押す。keydown から、doc-title と先頭行が期待どおりになった次のフレームの後まで。毎回、小さい文書を挟んで別の文書へ切り替える形にする。
- モード切替: Mod+Shift+F（フォーカス）と Mod+Shift+T（タイプライター）の keydown から、DOM の状態（.cm-md-dim、.cm-typewriter と余白の CSS 変数）が変わった次のフレームの後まで。
- docio: 標準ライブラリだけで時間を測る example（cargo run --release）。内容が毎回変わるよう、末尾の改行を足す、外すを交互にする。
- Tauri: HOME と CFFIXED_USER_HOME を計測用のディレクトリ（perf/out/tauri-runs/）へ向けて起動する。前回の文書（session.json）に fixture のパスを置いて、起動時に開き直させる。窓の出現は CGWindowList（Accessibility 権限不要）で観測し、OS へのキー入力・マウス操作は送らない。メモリは ps の rss を、アプリ本体と、起動前に無かった com.apple.WebKit.WebContent、GPU、Networking の合計とする。実ユーザーの Library の既知の場所の署名（サイズと mtime）を前後で比べ、2 回とも変化なし。
- p50、p95 は nearest-rank の分位点。

## 再現コマンド

```
npm ci --registry https://registry.npmjs.org
npx playwright install chromium webkit      # 公開 npm を使う
npm run perf                                # 全部（macOS 実機、約 6 分）→ perf/results/<日付>-<コミット>.json
npm run perf -- --quick --web-only          # 回数を減らした Web UI だけ（約 1.5 分）→ perf/out/（gitignore）
npm run perf:compare                        # perf/results/ の最新 2 件を比べる。20% 以上悪化があれば exit 1
npm run perf:compare -- <base.json> <new.json>
```

オプションは perf/run.mjs の冒頭を参照（--only web,docio,size,tauri、--browsers、--skip-build、--with-debug）。測定中は、同じマシンで重い処理（cargo、npm run test:e2e など）を並行して走らせない。CI では計測しない。

## 未計測

- Windows と Ubuntu の実機。
- 実 IME（macOS の日本語入力、Microsoft IME、Mozc）。IME は chromium の CDP の模擬だけで、webkit は未計測。
- Tauri 実機のキー入力から描画まで、スクロール、モード切替、ネイティブのダイアログを通した開く操作と保存（OS へ入力を送らない方針）。Web UI の値は WKWebView の値ではない（Playwright の webkit は別ビルド）。
- Tauri の「編集可能」の厳密な定義。窓の出現を代用した。
- cold の厳密な条件。ビルド直後の最初の 1 回だけで、OS のキャッシュ状態（再起動直後など）は制御していない。標本は 1 件。
- debug ビルドの起動時間（--with-debug で取れるが、この基準値では取っていない）。
- 保存後の fsync の影響を除いた値、ファイルがキャッシュに無い読み込み。
- 依存コンポーネントの一覧（仕様 §9.1 のパッケージサイズと依存コンポーネントのうち、依存は docs/licensing-audit.md を参照）。
